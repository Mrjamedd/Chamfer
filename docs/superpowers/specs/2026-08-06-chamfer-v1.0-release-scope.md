# Chamfer — Version 1.0 Release Scope

Date: 2026-08-06
Status: scope defined

## Product Summary

The app is a macOS note-cleanup application that connects to file-based note
folders and automatically improves Markdown and plain-text notes using AI.

Users connect one or more note vaults, configure which files may be processed,
select an AI model, choose a rewrite mode, and decide whether rewritten notes
should be applied automatically or placed into a Review queue.

The app is not intended to replace the user's note editor. It operates as an
automated cleanup, review, history, and restoration layer around existing note
files.

## Core Version 1.0 Goal

Version 1.0 must reliably monitor connected note folders, generate configurable
AI rewrites, safely apply or queue those rewrites, and preserve a complete
restorable history without risking silent data loss.

## Supported Platforms

Version 1.0 is a macOS application.

Windows, iPhone, iPad, Android, and web versions are outside the version 1.0
scope.

## Supported Note Sources

Version 1.0 supports file-based note sources only. Users can connect multiple
folders or full vault-style directories, including nested subfolders.

The app must support:

- Multiple connected vaults
- Nested folders
- Vault-wide configuration
- Folder-specific configuration overrides
- File-specific and folder-specific exclusions
- Optional inclusion of only selected folders
- Automatic exclusion of hidden files and system or application-generated folders

Non-file-based services are not supported in version 1.0.

## Supported File Types

Version 1.0 supports:

- Markdown files: `.md`
- Plain-text files: `.txt`

The following formats are outside the version 1.0 scope:

- `.rtf`
- `.docx`
- `.html`
- PDF
- Images
- Proprietary note-database formats

## File Monitoring

The app monitors connected vaults for supported file changes. A note can become
eligible for rewriting through either of the following systems.

### Inactivity-Based Rewriting

After a supported note changes, the app waits until the configured inactivity
period has passed before processing it. For example, a user may configure the
app to rewrite a note after it has not changed for 10 minutes.

The inactivity delay must be configurable.

### Scheduled Rewriting

Users can configure the app to scan and process eligible notes according to a
schedule or recurring interval.

Scheduling settings must support:

- Global defaults
- Per-vault overrides
- Per-folder overrides

The exact scheduling controls should follow the current application design and
technical implementation.

## Configuration Hierarchy

The app uses a layered configuration system. Settings may be defined at the
following levels:

1. Global defaults
2. Vault-specific overrides
3. Folder-specific overrides

More specific settings override broader settings. A folder override takes
priority over its vault settings, and vault settings take priority over global
defaults.

## AI Model Options

AI model selection and configuration have already been defined and should be
retained for version 1.0.

The app supports three model categories:

- Apple native models
- Downloadable local models
- Cloud-connected models

The existing model-selection interface, configuration behavior, privacy
disclosures, and cloud-processing safeguards should remain in place.

## Rewrite Modes

Version 1.0 includes five rewrite modes.

### Spelling Only

Correct spelling mistakes without intentionally changing grammar, formatting,
sentence structure, tone, or meaning.

### Grammar Only

Correct grammatical errors while preserving the user's wording and formatting
as closely as possible.

### Formatting Only

Improve the visual structure and formatting of the note without intentionally
rewriting its underlying prose. This may include changes such as spacing,
paragraph separation, heading structure, and list formatting, subject to the
user's preservation settings.

### Clarity Only

Improve readability, sentence clarity, and awkward phrasing without applying a
full spelling, grammar, and formatting cleanup unless those changes are
necessary for clarity.

### Full Cleanup

Apply all supported cleanup categories together:

- Spelling
- Grammar
- Formatting
- Clarity

Custom prompt construction and additional rewrite modes are outside the version
1.0 scope.

## Automatic and Review-Based Processing

Every rewrite mode can operate in either automatic or review-based mode.

### Review Mode

The generated rewrite is placed into the app's Review tab. The source file
remains unchanged until the user approves the entire rewrite.

Users can:

- Accept the full rewrite
- Reject the full rewrite
- Regenerate the rewrite
- Open the source note
- Undo an accepted rewrite through history

Version 1.0 does not support approving or rejecting individual changes within a
rewrite.

### Automatic Mode

The rewrite is applied directly to the source file after processing.

Automatic application must only occur when the user has explicitly enabled it
for the relevant global, vault, or folder configuration. No rewrite mode should
automatically apply by default without user configuration.

## Review Queue

The Review tab must organize pending rewrites clearly. Pending rewrites should
be grouped by connected vault and display:

- Note name
- File location
- Rewrite mode
- AI model used
- Time generated
- Current review status
- Outdated-source warning when applicable
- Failure or retry status when applicable

The default sort order is newest first.

The Review tab supports:

- Accept
- Reject
- Regenerate
- Open Note
- Bulk Accept
- Bulk Reject

Bulk actions apply only to rewrites explicitly selected by the user.

## Outdated Rewrite Handling

A rewrite becomes outdated when its source note changes after the rewrite was
generated but before the rewrite is approved or applied.

The app must:

- Clearly label the rewrite as based on outdated source text
- Allow the user to regenerate it from the latest version
- Allow the user to approve the outdated rewrite anyway
- Warn the user before applying it
- Create a fresh snapshot of the current file before applying the outdated rewrite

Approving an outdated rewrite may replace newer source text, but the replaced
version must remain restorable through history.

## Markdown Preservation

Markdown preservation behavior is configurable by the user. Users can decide
whether the app must preserve specific structures during rewriting, including:

- Headings
- Lists
- Links
- Images
- Embedded files
- Code blocks
- Front matter
- Task checkboxes
- Metadata
- Other Markdown syntax

Preservation settings may use the same global, vault, and folder override
hierarchy as other rewrite settings.

When preservation is enabled, the app should avoid modifying the protected
structure. When preservation is disabled, applicable rewrite modes may
reorganize or alter that structure.

If the app cannot safely process a note under the user's selected preservation
rules, it must leave the source file untouched and report the failure.

## Version Snapshots and Undo

The app creates a version snapshot before every applied rewrite. This applies
to:

- Automatically applied rewrites
- Manually approved rewrites
- Approved outdated rewrites
- Retried rewrites
- Rewrites applied through model fallback

Snapshots must allow users to restore the exact previous note version.

The app must provide:

- Easy undo for recent rewrites
- Per-note rewrite history
- Original and rewritten versions
- Restoration of earlier versions
- Clear cataloging of each rewrite inside the app

Backup copies should not be inserted into the connected vault unless the user
explicitly enables such behavior in a future release.

## History Retention

Rewrite history and snapshots are stored indefinitely in hidden local
application storage.

The standard History view displays the 200 most recent changes. A separate
button allows users to open and browse the complete stored history. The
complete history must remain restorable, including entries older than the most
recent 200.

History entries should include:

- Note name
- Original file path
- Rewrite date and time
- Rewrite mode
- AI model used
- Previous version
- Applied version
- Whether the rewrite was automatic or manually approved
- Whether the source was outdated
- Error, retry, or fallback information when relevant

## Search

Search is already implemented. Version 1.0 should retain the current search
behavior and search rules without redesigning or expanding the search system.
Any required compatibility work should preserve the existing user experience.

## Failure Handling

When a rewrite fails, the app must:

- Leave the source file untouched
- Display a clear failure state
- Provide a useful reason when available
- Allow the user to retry manually
- Retry later when appropriate for scheduled processing
- Record the failure in the app
- Avoid creating a misleading successful-history entry

Failures may include:

- AI model unavailable
- Cloud request failure
- Local model failure
- File permission failure
- Connected vault unavailable
- Unsupported file encoding
- File changed during processing
- Markdown preservation failure
- Storage or snapshot failure

## Model Fallback

Users may configure an optional fallback model. When the selected model is
unavailable or fails, the app may retry using the configured fallback model.

Fallback must be:

- Disabled unless configured by the user
- Clearly disclosed in the rewrite details
- Recorded in history
- Subject to the same privacy and cloud-processing rules as normal model selection

The app must not silently send note content to a cloud model when the user
expected local processing.

## Notifications

Notification categories are individually selectable by the user. Version 1.0
notification options include:

- Rewrite ready for review
- Automatic rewrite successfully applied
- Rewrite failed
- Connected folder unavailable
- Selected AI model unavailable
- Optional summary of completed and pending rewrites

Users must be able to enable or disable each notification category
independently.

## Background Operation

The app continues monitoring connected notes while its main window is closed.

Version 1.0 includes:

- Menu bar or background operation
- Optional launch at login
- Continued file monitoring while the app is running
- Continued inactivity-triggered processing
- Continued scheduled processing
- Background review generation
- Background automatic application when configured

Quitting the app completely stops monitoring and processing.

## Privacy and Cloud Processing

Privacy and cloud-processing behavior are already implemented and should be
retained for version 1.0.

The existing behavior should continue to:

- Distinguish on-device models from cloud-connected models
- Explain when note contents may leave the device
- Prevent excluded files from being processed
- Store credentials securely
- Keep snapshots and history locally
- Respect global cloud-processing restrictions
- Avoid unexpected model fallback to cloud services

## Data Safety Requirements

The app must prioritize file safety over completing a rewrite.

Version 1.0 must:

- Never silently overwrite a file after an unresolved processing error
- Create a snapshot before every applied rewrite
- Preserve recoverable copies of replaced content
- Avoid writing partial AI output into a source file
- Use safe or atomic file-writing behavior where practical
- Detect when a file changes during processing
- Clearly report unavailable folders and permission failures
- Recover safely after an application crash
- Avoid processing excluded files
- Avoid corrupting Markdown or plain-text encoding

No known issue that can cause silent data loss is acceptable for release.

## Existing Interface

Version 1.0 should use the existing application interface wherever behavior is
already implemented. The release scope should not introduce unnecessary
redesigns to:

- Search
- Model selection
- Privacy controls
- Cloud processing disclosures
- Existing navigation
- Existing note review interfaces
- Existing settings interfaces

Interface changes should be limited to what is required to complete, clarify,
or stabilize the scoped functionality.

## Onboarding

A dedicated onboarding flow is not required for version 1.0. Users configure
the app directly through the existing interface.

The app must still provide enough labels, empty states, and permission
explanations for users to understand what must be configured.

## Explicitly Out of Scope for Version 1.0

The following features are excluded:

- Apple Notes integration
- Notion integration
- Bear integration
- Google Docs integration
- Other API-based note services
- Database-backed note applications
- `.rtf` files
- `.docx` files
- `.html` files
- PDF rewriting
- Image or handwriting processing
- Windows support
- Mobile applications
- Web application
- Team collaboration
- Shared review queues
- Multi-user accounts
- Individual change approval
- Inline diff-by-diff acceptance
- Custom prompt builders
- Automatic note creation
- Automatic summarization as a separate feature
- Automatic tagging
- Automatic folder organization
- Cloud synchronization of rewrite history
- Cloud synchronization of snapshots
- Cloud synchronization of settings
- Dedicated first-launch onboarding
- Backup files inserted directly into note vaults by default

## Version 1.0 Release Criteria

Version 1.0 is ready for release when all of the following are true.

### File Reliability

- Connected vaults are monitored reliably
- Nested folders are detected correctly
- Exclusions are consistently respected
- `.md` and `.txt` files are processed without corruption
- File changes during processing are detected
- Unavailable folders and permission failures are handled safely

### Rewrite Reliability

- All five rewrite modes work
- Rewrites work across Apple native, downloadable local, and cloud-connected models
- Automatic and review-based workflows both function correctly
- User-selected Markdown preservation settings are respected
- Outdated rewrites are clearly marked
- Outdated rewrites can be regenerated or approved safely

### Review Reliability

- Pending rewrites appear correctly
- Whole-rewrite approval and rejection work
- Bulk accept and reject work
- Regeneration works
- Review metadata is accurate
- Source files remain unchanged before approval

### History and Recovery

- A snapshot is created before every applied rewrite
- Undo restores the correct prior version
- History entries are cataloged accurately
- The latest 200 changes appear in the standard History view
- The complete indefinite history is accessible
- Older versions remain restorable
- Crash recovery does not lose applied or pending state

### Scheduling and Background Operation

- Inactivity-based rewriting works at configured delays
- Scheduled rewriting works reliably
- Global settings and overrides resolve correctly
- Monitoring continues while the main window is closed
- Optional launch at login works
- Fully quitting the app stops processing

### Model and Failure Handling

- Model unavailability is reported clearly
- Manual retry works
- Scheduled retry works where appropriate
- Optional model fallback works only when configured
- Fallback usage is visible and recorded
- A failure never modifies the source file

### Privacy and Security

- Existing privacy controls remain functional
- Cloud processing remains clearly disclosed
- Credentials remain securely stored
- Local-only restrictions are respected
- Excluded files are never sent to an AI model
- Cloud fallback never occurs unexpectedly

## Testing

The app must be tested with:

- Small vaults
- Large vaults
- Deeply nested folders
- Large individual notes
- Rapidly changing notes
- Multiple connected vaults
- Mixed Markdown structures
- Front matter
- Code blocks
- Links and embeds
- Task lists
- Temporarily unavailable folders
- Unavailable models
- Interrupted cloud requests
- Application crashes during processing
- Conflicting source-file changes
- Full history containing more than 200 changes

## Version 1.0 Definition of Done

Version 1.0 is complete when a user can connect a Markdown or plain-text vault,
configure rewrite behavior, leave the app running, and trust it to clean
eligible notes automatically or queue them for review while preserving a
complete and easily restorable local history.

The defining standard is not the number of features. It is whether the app can
operate continuously and safely around a user's real notes without unexpected
rewriting, silent cloud use, file corruption, or unrecoverable data loss.
